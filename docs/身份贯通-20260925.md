# 第二/四页的数据身份贯通 · 2026-09-25

## 结论先说

**整合版本地一直在跑**（`127.0.0.1:3100/v28`，就是浏览器里那个标签页）。
"第二页永远是同一份老数据"不是没启动，是**只接了 UI、没接数据身份**：

- 第二/四页的后端是独立进程（`elfred-page2-api`，`:8000`），它**不认识**同事那套 session；
- 它当时写死了一个用户（`DEMO_USER_ID=demo`），所以**不管登录谁**，第二页都是同一份数据；
- 同事的第一/三页也**从来没有**往这个后端写过东西 —— 两边只有 UI 合在一起，数据层各过各的。

## 这次做了什么

### 后端（`elfred-page2-api`）

1. 新增 `app/identity.py`：按请求头 `X-Elfred-User` 取"这次请求是谁"，
   **没带就退回 `DEMO_USER_ID`**（脚本、探针、curl 的旧行为一字不变）。
   标识统一转小写，和上游注册时的归一保持一致，免得好端端一个人被拆成两份数据。
2. `main.py`（53 个接口）+ `personal.py`（5 个接口）全部改成按当前用户取数。
   接口上原有的 `paId` 参数保留为**显式覆盖**（排查/脚本用），不传就用当前用户。
3. `skill_store.user_skills(pa_id)`：**有主人的 skill 不再跨用户兜底**。
   之前无论谁进来都会看到 `skills-out/` 里那几条（等于把别人的卡摆给新用户）。
   现在：`user_id`/`owner` 匹配才算他的；没有主人的历史产物只归 demo。
   顺带把产出路径补上 —— `feedback.write_skill` 现在会把 `user_id` 写进 frontmatter，
   否则用户自己产出的 skill 也没法归到他名下。

### 前端（整合版）

1. `features/knowledge/page2-api.ts`：每个请求带上 `X-Elfred-User`；
   换人时**丢掉缓存再重拉**，并用 `loadSeq` 让只有最新那次能落地（否则会串号）。
2. 新增接缝件 `app/v28/core/page2-identity.tsx`：挂在 `RuntimeProvider` 里，
   把当前登录的 handle 推给上面的接口层。**同事的业务代码一行没动。**
