# 循环设计：任务契约 · 记忆中枢 · 能力进化

> 这份文档不按"能不能做"排，按产品的第一性排。工程顺序服从设计顺序。

## 一、产品的第一性

它不是"一堆 AI 工具"，是**一个随你做事而变强的私人智能体**。一次做事留下三样东西：

| | 是什么 | 谁记 |
|---|---|---|
| 做过的痕迹 | 这次做了什么、怎么做的、哪里被指正 | 执行器（他的 task/run/回执） |
| 记忆 | 你是谁、你要什么、你按什么来 | 中枢（EMOS） |
| 能力 | 这类事该怎么做 | 账本 + 孵化器（第二页的卡与 skill） |

三者不是三个模块，是**一个循环**：

```
        ┌───────────── 记忆（你是谁 / 你要什么 / 你按什么来）─────────────┐
        │                                                                │
        ▼                                                                │
  组装「任务契约」──► 执行（agent 按契约做）──► 用户裁定 ──┬──► 能力账（成果→卡分/等级/理解度）
        ▲                                                  │
        │                                                  └──► 记忆提取（含指正）──► 能力进化（新版 skill）
        └──────────────────── 陈旧 × 记忆里有新东西 → 问用户要不要更新 ────────────────┘
```

**所以"通不通"的标准不是两个库同步了没，是这个循环转不转得起来。**

按这个标准看现状：已有的桥接只做了「裁定 → 能力账」这一小段，属于**事后记账**。
循环里真正承重的两个半环是空的：**事前没有赋能**（agent 做事时不知道你的记忆和能力）、
**事后没有提取**（指正没进记忆，也没变成能力的规矩）。

## 二、三方职责（理念上的分工，不是代码归属）

| 角色 | 谁 | 只干一件事 |
|---|---|---|
| **执行器** | 他那边（第一 / 三页） | 接契约、跑、产回执 |
| **账本 + 孵化器** | 我这边（第二 / 四页） | 记账（成果 → 能力）+ 孵化（痕迹 → 记忆 → 新 skill） |
| **中枢** | EMOS | 唯一的记忆。所有入口汇入，所有 AI 工具从这里取 |

一句话：**能力属于用户，不属于任何一边。他是执行器，我是账本与孵化器。**
所以不需要"谁的成果写回谁的库"，需要的是**两边读同一份东西**。

## 三、四个环节各自的落点

### 环节 1 · 组装任务契约（做事之前）

契约长这样，全部是他那边 `task.create` **已经支持的字段**：
（`provider.generate` 把整个 goal 对象 `JSON.stringify` 进 user message，criteria / constraints 一定会到模型面前）

| 契约字段 | 内容 | 来自 |
|---|---|---|
| `goal` | 这次要做什么 | 用户本次的话 |
| `criteria` | 什么算做完 | 这条 skill 的验收用例（`tests/cases.json`） |
| `constraints` | 怎么做 + 你的规矩 | 这条 skill 的步骤（`workflow.json`）+ **用户历次定下的规矩**（skill 的 rules） |
| `source_refs` | 这次允许用哪些资料 | 用户选择 |
| `system` / `capability_id` | 谁来干 | 由 skill 的维度映射回去（交付→execute…） |
| （隐含）| **你的记忆** | 从 EMOS 召回的相关条目 —— 这就是"舒适区"落地的地方 |

**要建的**：我这边一个契约组装点 `app/contract.py`
`build_contract(user, goal, skill_name=None) -> {goal, criteria, constraints, sources, system}`。

**要改的（我这边，前端）**：第二页「用它做一件事」现在只往**前端本地状态**里塞了一条任务草稿
（`state.tasks` 每次 snapshot 刷新都被 `projectState` 重建 → 15 秒内蒸发），
并把"用哪张 skill"写进一个**没有任何代码读**的 `pendingSkill`。
改成：先取契约 → 真走 `runtime.command('task.create', 契约)` → 再跳对话。**skill 这才叫进场。**

### 环节 2 · 执行（做事之中）

不动。就用他现成的执行器：审批、预算、停止条件、回执、审查，都是他的。
契约之外的临时对话，走他现成的 ChatPage。

### 环节 3 · 回流（做事之后）——裁定分两笔账，同时写

| 写什么 | 落在哪 | 现状 |
|---|---|---|
| **能力账**：一条成果 → 卡分 / 等级 / 理解度 / 勋章 | 我这边 `Evidence` + `scoring` | ✅ 已通（桥接已在跑） |
| **记忆账**：这次的目标、回执、**你的指正** → 提取成记忆条目 | EMOS | ❌ 空 |
| **能力进化**：指正 → 规矩 → 这条 skill 出新版本 | 我这边 `apply_feedback` / `refine` | 机制已有，缺"从他的指正进来"这一段 |

**这一格是整份设计的关键。**产品原话是"某些步骤不符合我的风格，于是我指正 —— 在这个过程里产出 skill"。
也就是说：**指正不是抱怨，是 skill 的原料**。现在这条原料只在"我这边自己跑 skill"时才被用上；
用户在他那边做事时说的"不对"，全部掉在地上。

### 环节 4 · 周期性（陈旧 × 记忆里有新东西）

现有的：`skill_triggers`（7 天 ≥3 次 → `refine_ready`；7 天没用 → `stale`）、
`jev_judge`（问"记忆里有没有会改变它的新东西"）、`refine`（产出候选版本 + 快照 + 可回退）。

**缺的是被问的那一半**：判断依据是"记忆里有没有新东西"—— 只有记忆提取（环节 3 的记忆账）通了，
这句话才有内容。所以这一环不是独立工作，是环节 3 的下游。

## 四、记忆中枢（决策二在这里被化解）

产品原话：**"记忆系统相当于给整个软件的 AI 工具提供了一个舒适区。"**
这句话只有一个解释：记忆是**唯一**的中枢。两套记忆 = 两个舒适区 = 没有舒适区。

所以不是"他那份记忆要不要搬过来"，是**EMOS 要当上中枢**：

| | 内容 | 状态 |
|---|---|---|
| 入口 A（显式） | 他页面上用户确认/修正的那条（`memory.decide`）→ confirm→写 / correct→supersede / reject·delete→forget / defer→不写。**保留 scope、来源、修正链、有效期** | 要建（桥接的一段） |
| 入口 B（隐式） | 做事的痕迹（任务目标、回执、**指正**、对话）→ 提取成多维记忆 | 要建（我这边 `extract.py` 有雏形） |
| 出口 | **所有** AI 工具，首当其冲是他首页那个搜索：LLM 拆语义 → Jev 检索 → 命中记忆 → 给出带场景的结果 | **他那边要开一个只读的口** |

出口这条现在是断的，而且是产品最显眼的那条路：
**他首页的搜索现在检索的是他自己的对象库，根本没搜 EMOS。**
你举的"南方人搜羽绒服给东北的厚羽绒服"，靠的就是这一条 —— 场景来自记忆，不是来自文档。

还有一件只有单一中枢才做得到的事：用户改主意时，把所有**派生条目**一起标成"需要复核"。
他那边的 `memory.decide` 已经在这么干（会把 source_refs 指向它的条目置 `needs_review`），
但只在它自己的库里生效。两套记忆时，这一步永远做不干净。

## 五、一次真实的使用（拿着这个跑，就知道方案对不对）

> 学生第一次用：他在首页说"我下周考概率论，这套习题帮我做一下"。
>
> 1. **组装契约**：记忆里已有"他喜欢先给结论再推导"（上次的痕迹提取来的）；
>    如果已有一条「概率论习题讲解」的 skill，它的步骤和规矩也一起进来。
> 2. **执行**：他那边现成的执行器跑，出回执。
> 3. **他指正**："第二步跳步了。"
> 4. **回流，两笔账同时写**：记一条成果（能力账动）＋ 把"讲概率论不能跳步"提取进记忆，
>    并落成这条 skill 的规矩、出一个新版本。
> 5. **一周后**他再来：这条 skill 7 天没用过、记忆里多了"他提到考试在周三" →
>    系统问他：这条 skill 要不要按最近的情况更新一版。
> 6. **某天他搜"羽绒服"**：命中记忆里"国庆想去东北" → 给的是东北的厚羽绒服。

这条故事里的每一步，都能指到上面某个环节。指不到的，就是方案漏了。

## 六、落地顺序（按循环的承重，不按难度）

**第一步：立「任务契约」这个接口。**
不是因为容易，是因为它是**记忆和能力唯一同时进场的地方**：它不立，记忆提取和能力进化都没有出口，
后面填得再多也还是"两个库互相抄"。具体三件事：

1. 我这边加契约组装（skill + 记忆 → 契约）
2. 第二页「用它做一件事」改成真走 `task.create`（现在那条本地草稿是废的）
3. 回流补齐：验收时**同时**写记忆账 + 把指正落成 skill 规矩

**第二步：把记忆中介的两个入口接上**（显式 `memory.decide` + 隐式痕迹提取），
并让"陈旧 × 记忆有新东西"这条判定真的能问出口。

**第三步：两个要他开的只读口**（他的活，不是我的）：
① 首页搜索检索 EMOS；② 执行前读我们的 skill 形态。

## 七、边界（明确不做的）

- ❌ **不把我的成果/裁定写回他的 `objects`**。他那两页是"你做过什么"的事件流水，
  我这两页是"你因此成了什么样"的资产账。资产账必须是从流水**推导**出来的；
  反过来写，就是两个源互相写，谁都不确定。
- ❌ 不新造第二套记忆。他那边 `memory` 对象是**用户显式确认的入口**，不是另一个真相。
- ❌ 不新造 skill 格式。现在 `SKILL.md + workflow + examples + tests + provenance` 那七件套就是形态，
  两边都读它。
